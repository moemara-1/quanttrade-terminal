# Perpetual trading desk implementation plan

**Superseded:** The user requested one terminal. The implemented architecture is documented in [QuantTrade single terminal](2026-10-05-quanttrade.md); the separate prototype no longer launches or serves its UI.

**Goal:** A local manual and agent-assisted desk for Hyperliquid and Lighter, with the user approving every order.

**Architecture:** Reuse the Pairlens chart engine and retain its full terminal as the companion analysis workspace. Public exchange APIs supply current market data. A local Node service owns immutable proposals, risk checks, approval, audit records, and a restricted Hummingbot API client. Hummingbot owns exchange credentials and signing. No agent receives the approval credential or raw Hummingbot access.

**Tech stack:** TypeScript, React, Vite, Node 24 SQLite, Pairlens charts, Hummingbot API and its core exchange connectors.

## Assumptions and scope
- Personal local use on this Windows machine; localhost binding, no cloud deployment.
- Agents prepare orders, the human approves execution. Paper mode is the default.
- Initial tickets support simple opening market/limit orders. Leverage configuration and native protective/closing orders stay in the venue until separately implemented and verified. Never silently pretend unsupported order semantics work.
- Do not combine the upstream repositories or modify their source unnecessarily. Pin their revisions and retain their licenses.
- Live exchange verification requires Docker/Hummingbot and a user-configured account; no trading credentials are requested in chat.

## Tasks
1. Pin upstream revisions, inspect exchange contracts and reuse boundaries.
2. Write failing tests for proposal validation, expiry, duplicate/concurrent approval, uncertain execution, halt, role boundaries, and limits.
3. Implement SQLite persistence and restricted execution client. A timeout becomes unknown and cannot be automatically retried. Revalidate market data at approval.
4. Implement public market readers for both venues, with explicit failures, bounded calls, normalized decimal values and tests.
5. Build the visual control desk: watchlist, Pairlens chart, order book, manual tickets, agent requests, approvals, audit and service state. Delegate visual implementation as requested.
6. Add optional model-backed proposal generation. Validate model output with the same order schema, no execution tools.
7. Add setup/run documentation, upstream provenance, local configuration and agent API examples.
8. Run type checking, unit/integration tests, production build and browser inspection. Report separately what is verified and what requires live account setup.

## Acceptance criteria
- Public market data from both target venues is usable without keys or Docker.
- No order can be sent through the agent credential.
- Human approval references a stored immutable proposal and checks freshness/limits again.
- Repeated approval cannot duplicate exchange submission, including after uncertain failures or restart.
- Paper and live activity are clearly separated in the UI and persistence.
- Live orders are never reported as filled merely because Hummingbot returned a client order ID.
- Local app runs and builds; integration limitations remain explicit.
