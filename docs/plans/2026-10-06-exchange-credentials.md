# QuantTrade exchange credentials

The existing Connect Exchange wizard accepts actual Hyperliquid and Lighter API credentials. Hosted users authenticate through the existing private web login; a protected proxy endpoint establishes an eight-hour HttpOnly, Secure, SameSite Strict operator session. Browser signing keys are transmitted only to the same-origin HTTPS bridge, then discarded; only safe connection references remain in native credential state. Other exchanges keep their existing device vault behavior.

The bridge binds every credential operation to account `desk`, validates exact venue fields, serializes updates per venue and never returns signing keys. Agent tokens cannot configure credentials or approve execution, even if presented alongside an operator cookie. Mutations authenticated by cookie require the exact terminal origin. Hummingbot encrypts venue secrets using its server-only configuration password.

Credential creation includes read-only authorization checks inside Hummingbot's existing rollback boundary. Lighter verifies the actual signer key; Hyperliquid checks the derived wallet or approved API agent and rejects failed verification. Public account lookup alone is insufficient. Disconnect removes the server credential. Exchange balances are read-only; paper orders and positions remain simulated. The user can select Live independently for each venue: manual orders execute on order submission, while AI-prepared proposals remain pending until explicit approval. No real trade is placed during implementation or verification.

Verification covers role boundaries, session issuance/spoofing/CSRF, fixed account and connector targeting, key validation and redaction, credential-check rollback insertion, native persistence without secrets, reconnection and wizard behavior, production build and hosted endpoints. Deploy a separate release and retain the previous release for recovery. No user signing keys are needed to implement or verify rejection paths.
